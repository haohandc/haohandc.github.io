## maze-escape

![](/assets/img/media/2026_5_25/image-20260517135402-1nfua1r.png)

woc，搞什么，怎么难度突变？。以下是AI的题目分析，网上暂时也没找到题解

---

### [分析对象]

​`maze-escape` — Linux x86-64 ELF, 18KB, 58个函数, 33个字符串

### [核心逻辑]

**数据流：**

1. 读取用户输入（格式 `tjctf{...}`​，字符集 `abcdefghijklmnopqrstuvwxyz0123456789_`）
2. 依次读取 11 个 `breadcrumbs/breadcrumb_%02d.bin` 文件 → 异或合并成一个 32 字节密钥
3. 读取 `maze_core.bin`（14KB），用上述密钥解密
4. 解析 maze 头部（校验 magic=945183309, 版本=3, 迷宫维度 ≤32, 目标位置等）
5. 将输入字符通过查表映射到迷宫数据中，做多层运算：

   - 查表置换（S盒）
   - 有限域上的矩阵乘法（模 0x25 和 0xFB）
   - 64位滚动哈希验证（类 TEA/XTea 结构）
   - 最后比对 v110==v154 和 v115==v156

**关键辅助函数：**

- ​`sub_22B0`​ → `return a1 == a2`（用 LAHF/SAHF 混淆）
- ​`sub_22C0` → 自定义哈希（魔数 0x6D2B79F5, 0x27D4EB2D, ROL 11）
- ​`sub_2310`​ → `read_file()`
- ​`sub_2300` → 读8字节

### [缺失提示]

- breadcrumb 文件和 maze_core.bin **数据文件齐全**
- breadcrumb 数据看起来是加密/随机状态，需要理解解密算法才能提取明文
- maze_core.bin 头部也无明文魔数，说明解密是 breadcrumbs 驱动的
- 输入长度 = 迷宫节点数（ptrb），埋点在头部的校验中

### [难度评估]

| 维度             | 情况                                   |
| ---------------- | -------------------------------------- |
| **加壳/混淆**    | 无加壳，仅少量运算混淆                 |
| **函数量**       | 58个，核心在 main(~3000行反编译)       |
| **算法复杂度**   | 高 — 多轮密钥派生 + 矩阵乘 + 滚动哈希  |
| **依赖数据文件** | 12个 .bin，全部依赖                    |
| **反调试**       | 无                                     |
| **符号/Strip**   | Strip过（36个命名函数，22个anonymous） |
| **WriteUp**      | 网上 **0** 个，比赛期间 **0** 解       |

**结论：难度非常高（Hard/Expert）** 。原因不是反调试或加壳，而是：

- 算法链很长：breadcrumb 解密 → 迷宫头部校验 → 字符映射 → 置换 → 矩阵运算 → 滚动哈希 → 两路64位比对
- 每一步都依赖上一步的结果，传统"打补丁"行不通
- 适合用 **符号执行（angr）**  或 **Z3 约束求解** 处理，但 11 个 breadcrumb 的随机性需要先逆向出密钥派生逻辑

如果想继续深入，我的建议是：**先用动态调试（gdb）跑一下**，观察 breadcrumb 解密后的迷宫头部数据是什么结构，再决定后续方案。
